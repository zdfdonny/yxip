# yxip · 优选IP 聚合与优选流水线

从多个公开上游采集候选 IP，**做真实 TCP 握手测速**，按综合评分排序，产出当前网络环境下最优的 N 个 IP。

输出同时面向人和机器：`ip.txt` 是客户端可直接消费的清单，`best.json` 带完整的测量与评分明细，便于复现与二次处理。

> ⚠️ **免责声明**：本仓库仅做公开数据聚合与连通性测量，不托管任何节点、不提供任何代理服务。
> 列表中的地址均来自第三方公开清单，可用性、安全性与合规性请自行判断。

---

## 特性

- **真实测速，而非排序搬运** — 每个候选都做 TCP 握手实测（3 次采样），延迟与成功率直接进入评分
- **三类候选语义分离** — Cloudflare anycast 边缘 IP、中转 `ip:port`、通用开放端口代理，各自独立分类，可按需筛选
- **CF 网段强制校验** — 所有 CF 类候选对照 Cloudflare 官方 CIDR 校验，页面噪声与非 CF 地址不会混入
- **绝对延迟量纲** — 指数衰减而非 min-max 归一化，评分不受池内极值影响，跨次运行可比
- **地区均衡** — 每个地区都有保底名额（`ceil(top_n / 地区数)`），不会被 RTT 最低的一两个地区吃满；候选不足的地区按实际数量入选，空缺由其他地区补足
- **多样性约束** — 同 `/24`、同 **ASN**（按占比）、同 IP 三个维度都设上限，避免一张榜实际只有一条线路；软约束在备选不足时自动放宽以补足条数
- **产物不再被一次故障打坏** — 源全部/大半失效导致的产出腰斩会被识别，保留旧榜拒绝覆盖
- **可解释** — 每次运行打印按类型 / 地区 / 数据源的连通画像，源失效一眼可见
- **零配置自检** — `--self-test` 全离线覆盖解析、分类、评分、筛选逻辑
- **反查省** — 只为「评分靠前的候选 + 入选者」查询 ip-api（默认 ≤ 300 个 IP = 3 个 batch 请求），全部落本地缓存
- **多机各一份榜单** — `--name home` / `--name "{host}"` 让每台电脑产出自己的 `ip-<name>.txt`，`--also ip.txt` 可同时保留一份标准名

## 快速开始

```bash
pip install -r requirements.txt

python collect_ips.py --self-test      # 离线自检，不联网
python collect_ips.py                  # 完整流水线，产出 TOP 30
python collect_ips.py --top 50         # 自定义产出条数
python collect_ips.py --kinds cf       # 只要 Cloudflare anycast
python collect_ips.py --kinds relay    # 只要中转节点
python collect_ips.py --out x.txt      # 输出到指定文件（JSON 同名）
python collect_ips.py --name home      # 输出 ip-home.txt / ip-home.json（多机场景）
python collect_ips.py --name "{host}" --also ip.txt   # 按主机名命名，并同步一份 ip.txt
python collect_ips.py --no-measure     # 只跑采集与分类（调试用）
python collect_ips.py --force          # 忽略产物回落保护，强制覆盖
```

一次完整运行约 90 秒（600 个候选 × 3 次采样）。

## 输出

### 文件命名

默认写出 `ip.txt` + `best.json`（与旧版完全一致）。多台电脑各跑各的时，用 `--name`
给榜单起名，避免互相覆盖：

| 参数 | 产出 |
|---|---|
| （不给） | `ip.txt` / `best.json` |
| `--name home` | `ip-home.txt` / `ip-home.json` |
| `--name "{host}"` | `ip-<主机名>.txt`（本机为 `ip-Donny-PC.txt`） |
| `--name "{host}-{date}"` | `ip-Donny-PC-20261027.txt` |
| `--out my.txt` | `my.txt` / `my.json`（优先级最高，会覆盖 `--name`） |

- 占位符：`{host}` 主机名、`{date}` 当天日期 `YYYYMMDD`，可组合使用；
- `--also ip.txt`（可多次或逗号分隔）让**同一次运行**额外再写一份 txt 副本——
  客户端已经指向 `ip.txt` 时，既能保留多机各自的榜单，又不破坏原有引用；
- 名字会被清洗：路径分隔符、`..` 等一律替换，不会写出目录之外；
- `--also` 只写 txt 副本（客户端消费的就是 txt），不再多生成 JSON；
- 产物回落保护按**主文件**判定：`ip-home.txt` 的基线只来自它自己，多机互不干扰。

> 为什么要按机器分文件：「优选」本质是**从某个网络位置测得的延迟排序**，
> 不同机器（家宽 / 公司 / 境外 VPS）跑出来的榜单本就该不一样，混在一个 `ip.txt` 里
> 互相覆盖没有意义。每台机器产出自己的 `ip-<name>.txt`，客户端按使用场景挑一份。

### `ip.txt`

每行 `端点#地区-排名-ISP`。整行只有一个 `#`，其后三段用 `-` 连接，**按评分从优到劣排序**，排名即质量位次：

```
103.238.227.212:8443#HK-1-Xnnet LLC
116.206.178.91:443#HK-2-Xnnet LLC
103.115.64.44:443#HK-3-Cloudie Limited
```

- 地区段：`relay` 是数据源自带的地区码（`HK`/`JP`/`SG`/`KR`/`TW`）；
  **`cf` 显示为 `CF`**——anycast IP 没有固定地区（见下节）；
- 无端口的行是 Cloudflare anycast 边缘 IP，客户端按 `:443` 使用；
- `-1` 表示**当前排名第 1**，不是稳定 ID。测速结果每次都变，名次随之变化。
  需要跨运行稳定的标识请用 `best.json` 里的 `stable_id`。

### `best.json`

含每个入选者的完整指标，以及本次运行的评分权重与测量参数：

```json
{
  "rank": 1,
  "endpoint": "103.238.227.212:8443",
  "ip": "103.238.227.212",
  "port": 8443,
  "kind": "relay",
  "region": "HK",
  "label": "HK",
  "country": "香港",
  "city": "旺角",
  "isp": "Xnnet LLC",
  "asn": "AS6134 XNNET LLC",
  "rtt_ms": 34.96,
  "success_rate": 1.0,
  "score": 72.8,
  "sources": ["zip"],
  "stable_id": "relay:103.238.227.212:8443"
}
```

### `enrich_cache.json`

ISP / ASN / 归属地反查的本地缓存，避免重复请求 ip-api 触发速率限制。
仅保留当前相关的条目，不会无限膨胀。

## 关于 CF 的"地区"

`cf` 类候选的 `region` **恒为空**，在 `ip.txt` 里显示为 `CF`。这不是缺失，是刻意的：

Cloudflare anycast IP **没有固定地理落点**。同一个 IP 在全球数百个 PoP 同时广播，
BGP 把每个用户导向最近的节点——你在香港连它落在香港，在洛杉矶连它落在洛杉矶。
所以「这个 IP 属于哪个地区」对 anycast 本身是伪命题，收集时会直接丢弃数据源给的地区标记。

> ⚠️ **`cf` 条目的 `country` / `city` 来自 ip-api，是 IP 的注册地，不是真实服务节点。**
> 例如 `104.26.4.90` 的注册地在加拿大，但实际很可能把你送到香港。排查 CF 延迟问题时
> 不要以这两个字段为依据——要确认真实落点，需要看响应的 `cf-ray` 头或请求 `/cdn-cgi/trace`。

`relay` 条目则相反：它是具体的服务器，`country` / `city` 由 ip-api 反查得到，可放心参考。

## 工作原理

```
采集（8 个上游 + 可选本地表）
  → CF 网段校验（官方 CIDR + 内置回退）
  → 语义分类 cf / relay / proxy
  → 去重合并（同端点合并，保留多源 provenance）
  → 预排序 + 分地区轮转取样（实测预算 600）
  → TCP 握手实测（3 次采样 / 2.5s 超时 / 64 并发）
  → 硬门槛过滤 + 四维加权评分
  → 预取评分靠前候选的 ASN（≤ 300 个 IP，走缓存）
  → 多样性筛选（地区保底、/24、同 IP、ASN 上限，不足额时按 /24 → ASN → 地区 顺序放宽）→ TOP N
  → 产物回落保护（明显缩水则保留旧榜、拒绝覆盖）
  → 对入选者批量反查 ISP/ASN（此时基本全部命中缓存）
  → 落盘
```

**分地区轮转取样**是为了让每个目标地区都有机会进入实测，而不是被候选数量最多的地区吃满预算。
做法是先把候选按 `pre_score`（源收录数 + 上游测速值 + 是否有地区 + 是否 CF）排序，
再按地区分桶后轮流取，直到达到实测预算。

**ASN 预取**是 ASN 去重的前置条件：`as` 字段原本只在反查阶段才有，而筛选发生在反查之前。
现在先对评分靠前的 `ASN_PRECHECK_LIMIT`（默认 300）个候选取一次归属，再进筛选；
预取和 `enrich` 共用 `enrich_cache.json`，所以入选者不会再被请求第二次。

**只查少量 IP**是关键优化：ip-api 按 IP 计费、按 batch 限速，把范围压到
「评分靠前 300 + 入选 30」并全部走缓存，一次运行最多 3~4 个 batch 请求。

## 评分模型

总分 = 加权平均（分母只计实际可用的分量）：

| 分量 | 权重 | 说明 |
|---|---|---|
| 延迟 | 0.65 | `exp(-rtt / 100ms)`，**绝对量纲** |
| 握手成功率 | 0.20 | 3 次采样中成功的比例 |
| 多源共识 | 0.10 | 被 N 个上游同时收录，`min(N,3)/3` |
| 上游测速值 | 0.10 | 上游自带的 kB/s 标注，覆盖率 < 10% 时自动弃用 |

### 为什么用指数衰减而不是 min-max 归一化

min-max 依赖候选池的**极值**。只要池里出现一个 1300ms 的离群候选，200ms 的候选就会拿到 0.87
的延迟分、"接近满分"——这不合理。指数衰减是绝对量纲，与池内其它候选无关，
既不会被离群值污染，也让不同次运行的分数可以直接比较。`--self-test` 里有对应回归用例。

### 淘汰规则

以下候选不参与排名：

- 3 次握手全失败，或成功率低于 `MIN_SUCCESS_RATE`（0.30）
- 不在 `ALLOWED_REGIONS` 目标地区内（仅针对 `relay`）
- 撞上多样性上限（同 `/24` 的 CF IP 最多 2 条；同一 `/24` 的中转节点最多 3 条；
  同一 IP 的中转端口最多 2 条；同一 ASN 最多占榜单 12%，仅 `relay`；
  同一地区最多占 `ceil(top_n / 地区数)` 条，即地区保底名额）

> 多样性上限只在**备选够用**时生效：若严格执行后凑不满 `--top`，会按
> `/24` → ASN → 地区保底 的顺序逐级放宽（同 IP 上限永不放宽）。
> 这样加严多样性不会让榜单变短——变短会误触发产物回落保护。

### 地区均衡

`pick_top` 加地区约束之前是**纯按评分取**，所以榜单会被 RTT 最低的一两个地区吃满
（实测 HK 曾占 14/30 = 47%，SG 只剩 1 条，而那条 81ms 其实很有竞争力）。

现在每个地区的名额上限是 `ceil(top_n / 有候选的地区数)`，`--top 30` 且 5 个地区都有候选时
就是每地区 6 条。实测分布从 `HK 14 / JP 10 / KR 3 / SG 1 / TW 2` 变成
**`6 / 6 / 6 / 6 / 6`**，最大占比从 47% 降到 20%。

两个配套约定：

- 地区保底是**最后一档**才放宽的约束——先容忍同 `/24`、再容忍同 ASN，才轮到放弃地区代表性；
- 保底阶段**不吸收 `cf`**：anycast 没有地区配额，若让它在这几轮自由入选，会提前吃掉本该
  留给小地区的名额（实测被 CF 抢走 7 个）。`cf` 只作为 relay 凑不满时的补位。
  所以混合榜里 `cf` 基本不会出现，要 CF 请用 `--kinds cf`。

> ⚠️ **这是要付出延迟代价的**：为凑满名额会拉进该地区较慢的节点。实测 `--top 30` 时
> `>200ms` 的条目从 0 条增加到 6 条（最慢 314ms）。这是地区均衡的固有成本，不是 bug；
> 只想要最快的一批就把 `REGION_BALANCE` 设为 `False`。

为什么 ASN 这一维不可省：`/24` 只能挡住"同一个 /24 里塞了几十个 IP"的密集刷榜，
而 NTT、AWS 这类上游是**横跨多个 /24** 铺开的——实测中 `/24` 上限跑完，仍有 11/50 条
出自同一个上游。要在"看起来 50 条"和"实际几条线路"之间做区分，只能按 ASN 数。

`cf` 不受 ASN 上限约束：anycast 无论落在哪个段都是 Cloudflare 的 `AS13335`，限了会把
CF 类候选全部灭掉。反查失败（`as` 为空）的 `relay` 同样不参与 ASN 限制，避免 ip-api
不可用时把中转候选全灭。

被淘汰的候选仍会出现在实测统计里，方便看出是哪个源或哪个地区在拖后腿。

## ⚠️ 最重要的限制：结果只对"测量点"有效

"优选IP"的本质是「**从某个特定网络位置测得的、通往目标的 TCP 握手延迟最小者**」。
它是一个与观测点强相关的量，**无法通过共享清单传递给其他网络环境**。

因此：

1. 排名反映的是**运行脚本那台机器的视角**；
2. 在 GitHub Actions（美国 runner）上跑出来的榜单，对**中国大陆用户几乎没有参考价值**——
   候选池、RTT 排序、甚至哪个源能连通，都会完全改变；
3. 想要对某地用户有效的榜单，必须在**该地网络环境下运行**（本地跑，或自建位于目标地区的 runner）；
4. 客户端侧仍应保留 `url-test` / 自动选路，把本清单当作**候选池**而非最终答案。

本项目负责把上万个候选筛成几十个「此刻确实能连、延迟相对低、有多个上游背书」的端点，
省掉手工试错；它不能替你做终端网络环境下的最终判决。

## 配置

全部集中在 `collect_ips.py` 顶部的配置块。

### CF anycast 与中转是两种产品

默认混合排名（`ALLOWED_KINDS = ("cf", "relay")`）。三者语义不同：

- **`cf`**：Cloudflare anycast 边缘 IP，无端口，作为 CF 前置节点的**入口**使用（实测走 `:443`）；
- **`relay`**：数据源自带的 `ip:port` 中转节点，是**独立节点**；
- **`proxy`**：通用开放端口代理，端口语义不可控（可能只是某台机器的 RDP / SMTP），默认不入选。

只要其一时用 CLI 切换，无需改代码：

```bash
python collect_ips.py --kinds cf      # 纯 CF 榜
python collect_ips.py --kinds relay   # 纯中转榜
```

> 混合榜里 CF 常常一条都进不了前列——因为实测中 CF anycast 的 RTT 普遍高于亚太中转节点
> （前者 130ms+，后者 36ms 起）。这是真实测量结果，不是筛选错误。

### 常用配置

| 配置 | 默认 | 作用 |
|---|---|---|
| `TOP_N` | 30 | 产出条数（也可用 `--top`） |
| `ALLOWED_KINDS` | cf + relay | 参与排名的类型（也可用 `--kinds`） |
| `ALLOWED_REGIONS` | HK/SG/JP/KR/TW | relay 的地区白名单 |
| `MEASURE_MAX_CANDIDATES` | 600 | 进入实测的候选上限 |
| `MEASURE_SAMPLES` / `MEASURE_TIMEOUT` | 3 / 2.5s | 采样次数与单次超时 |
| `MEASURE_WORKERS` | 64 | 测速并发 |
| `REGION_BALANCE` | True | 地区均衡（每地区保底 `ceil(top_n / 地区数)` 条） |
| `MAX_PER_CF_24` | 2 | 同 /24 的 CF IP 上限 |
| `MAX_PER_RELAY_24` | 3 | 同 /24 的中转节点上限 |
| `MAX_PER_RELAY_IP` | 2 | 同一 IP 的中转端口上限 |
| `MAX_PER_ASN_RATIO` / `MAX_PER_ASN_MIN` | 0.12 / 2 | 同一 ASN 的占比上限与最小条数地板（`--top 50` 时为 6 条，`--top 30` 时为 4 条） |
| `ASN_PRECHECK_LIMIT` | 300 | 为 ASN 去重预取归属的候选数（按评分取前 N） |
| `MIN_OUTPUT_RATIO` | 0.5 | 产物回落保护阈值（低于上次该比例则拒绝覆盖） |
| `MIN_SUCCESS_RATE` | 0.30 | 握手成功率门槛 |
| `LATENCY_TAU_MS` | 100.0 | 延迟衰减常数 |
| `MIN_UPSTREAM_COVERAGE` | 0.10 | 上游测速值覆盖率低于此值时弃用该分量 |
| `LOCAL_CITY_FEED` | `city.txt` | 可选本地地区表路径 |
| `OUTPUT_ALIASES` | `()` | 每次运行都要额外写的 txt 副本，例如 `("ip.txt",)` |

> 为什么需要多样性上限：不设限时，同一个 `/24` 或同一台机器的多个端口会刷满整张榜，
> 看起来「又快又多」，实际只是一条线路。
>
> 其中 `relay` 才是重灾区：它原本只被「同一 IP」这一条挡住，而机房的邻居 IP 属于
> 主机商池子里的不同地址，`MAX_PER_RELAY_IP` 完全管不到。
>
> 加 `MAX_PER_RELAY_24` 只解决了一半：实测中 `/24` 上限生效后，50 条的榜里仍有
> **11 条来自同一个上游**（`207.57.0.0/16`，NTT）——因为这类上游横跨多个 `/24`。
> 真正的「一条线路」判据是 ASN，所以还要按 ASN 限流。
>
> ASN 上限按**占榜单比例**（`MAX_PER_ASN_RATIO`）而不是绝对值：绝对值会让 `--top`
> 变小时同一个上游占比反而失控——实测 30 条的榜里单个 ASN 曾占到 **6/30 = 20%**，
> 而 50 条时才是 12%。换算后 `--top 30` 收紧到 4 条、`--top 100` 放宽到 12 条，
> 单 ASN 占比稳定在 12% 上下。
>
> 三个维度的严格程度是「同 IP > 同 ASN > 同 /24」：同一个 IP 的多个端口既不会吃满
> `/24` 配额，也不会吃满 ASN 配额。

### 源失效与产物保护

单个源失败不会中断流水线，但会明显改变产物，所以有两道可观测性 + 一道兜底：

1. **数据源健康汇总** — 每次运行打印 `数据源健康: 成功 N/M` 和失败源名单；
2. **主力源专项告警** — `zip` 是唯一的 `region_feed`，relay 类候选全部来自它。
   它失败时会额外提示「relay 类候选将完全缺失」，此时产物最多只剩 `cf`；
3. **产物回落保护** — 落盘前比对上次产出，本次条数不足基线（`min(上次条数, --top)`）
   的 `MIN_OUTPUT_RATIO`（默认 50%）时，判定为数据源异常，**保留原有 `ip.txt` 不覆盖**，
   以退出码 1 结束并打印原因。

基线取 `min(上次条数, --top)` 是为了不误伤主动调小 `--top` 的场景。
确认缩水是预期结果（例如上游大面积下线）时，用 `--force` 强制覆盖。
